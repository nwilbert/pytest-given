# Writing scenarios

When decorating a test with `@scenario`, the goal is a report that reads as a truthful behavioural spec.

## What to decorate

- **Convert behaviour, not plumbing.** Decorate tests that assert a rule (a calculation, a validation, a dispatch decision). Leave trivial getters, constructors, and dataclass round-trips as plain tests — they add report noise, not behaviour.
- **Write the narration first.** For a new scenario, write the `@scenario` name and the step texts before the bodies — the narration is the spec the implementation fills in (the narration-level face of the TDD convention).

## Phase structure

- **Every step maps to load-bearing code.** `given` arranges, `when` performs the one call under test, `then` asserts its result. Never write a placeholder step like `with given(...): pass` — a step with no code is a lie in the report. Delete it.
- **Put the system-under-test call in `when`, not folded into the `then` assertion.** Prefer `with when(...): result = sut(x)` then `with then(...): assert result == …` over `with then(...): assert sut(x) == …`. The report should show the action, not hide it inside a check.
- **One outcome per `then`.** When an action has two independent outcomes (a return value *and* a state change), give each its own sibling `then` step. A `then` narration that needs an "and" is two steps written as one — split it so each outcome is visible and filterable on its own.
- **When the construction *is* the action under test, `when` builds it and `given` shows only the input.** Don't fold the constructor into the `given` (it hides the action) or into the `then` (it hides it inside a check). If a scenario asserts a property of a freshly-loaded/parsed/built object — `Order(lines)` computes its total, `parse(doc)` yields all rows — split it: `given` holds and (when useful) `attach`es the raw input (the source document, the line items); `when` runs the constructor; `then` asserts on the result. A two-phase `given` that both arranges the input *and* constructs the object under test is the most common missed `when`.
- **Two phases is fine when honest — but rarer than it looks.** If the assertion inspects a *static property of the arranged state* (not a return value of an action), `given` + `then` is truthful and you shouldn't invent a `when`. Most two-phase scenarios aren't that; they're the missed construction above. Likewise a pure "constructing X raises" check needs no `given`.
- **Step structure must not depend on parameter values.** Parametrized scenarios render every row against case 1's step structure, so narration that branches on a parametrize value (a conditional `with given/when/then(...)`) silently shows case 1's shape for all rows. If the steps genuinely differ per case, split into separate `@scenario` tests.

## Arrangement

- **Surface the arrangement as a `given`, don't hide it in the assertion — or in the `when`.** If a scenario feeds the action a module constant or a value it builds on the fly (a document string, a path, a list of rows), bind that input in a `given` step rather than passing the literal straight into the `when`/`then`/`pytest.raises` call. For a one-off, construct it in an explicit `with given(...)` block. The same applies to state-mutating setup calls (inserting credit, seeding a database): they belong in a `given` ("credit of 200 inserted"), not in a second `when` — a scenario with two `when` steps usually hides an arrangement in the first one.
- **Decide a fixture's `given` by what it holds, not by the fact that it's a fixture.** A fixture carrying a **domain value the scenario is about** — an actor, a document, an entity it acts on — *is* arrangement: decorate it `@given('…')` (a `@pytest.fixture` wrapped with `@given`) so it surfaces as a `given` step, the same way you'd narrate that value if you built it inline. A fixture that is only **infrastructure** (a `Glossary()`, `tmp_path`, a connection) stays a bare `@pytest.fixture` — it's plumbing, not story. The deciding test: *would you write a `given` for this value if you constructed it inline in the test body?* If yes, decorate the fixture, so fixture-sourced scenarios read the same as inline ones. Don't leave the same arrangement visible in one scenario and hidden in another just because one built it inline and the other pulled a fixture.
- **A parametrized value can be a `given` too.** Inputs from `@pytest.mark.parametrize` already show in the parameter table, so they don't *need* a `given`. When one reads as an *arrangement* the reader should see named up front (rather than as the subject of the action), surface it as a `given` via `Annotated[..., given(Template('… {col} …'))]` on that parameter. For a one-arg pure function either reading is honest — it's a judgment call, not a mandate.
- **Attach the concrete artifact a `given` can only describe.** When a step arranges a multi-line input the step text abstracts — a document, a config snippet — `attach('label', text)` it onto that step (`attach` is a top-level `pytest_given` export, like `given`) so a report reader sees the real input inline instead of chasing a source link. Attach on the arranging step (`given` or a `@given` fixture body), never on `when`/`then`, and only for inputs the step text can't carry (skip it when the arrangement is a bare path or a small value already shown in the parameter table).

## Expected raises

- **Keep pytest-given narration and real assertions separate.** Nest the vanilla `pytest.raises` inside the narration — never fold it into a narration-named helper. The report step and the actual assertion stay visibly distinct constructs. (Exempt tests from lint rules that forbid nested `with` statements — e.g. ruff `SIM117` — so this nesting is allowed.)
- **Narrate an expected raise as `when_then` — the action and the raise are two steps.** The raise *is* an outcome, so keep it distinct from the action that triggered it: `with when_then('the action', 'an `InsufficientCredit` error is raised'), pytest.raises(Exc, match=…): sut(x)` emits a `when` (wrapping the call) and a sibling `then` (the outcome). Write the `then` as a real outcome, not the bare mechanism: name the exception type (`'an `InsufficientCredit` error is raised'`) and, when the `match=` pins a specific message, reflect that finding in domain terms (`'the shortfall amount is reported'`). Avoid a contentless `'it raises'`. The duty runs both ways: if the `then` promises message specifics — it names the offender, offers a suggestion, carries file:line context — the `match=` must be tight enough that only a message with that detail passes; a loose pin (`match='column'` under "names the missing column") leaves the narrated specificity unverified, so it can regress while the test stays green. The `when` runs the body; the `then` is emitted once the inner `pytest.raises` swallows the error.

## Vocabulary and tags

- **Narrate in glossary vocabulary.** Reference glossary terms via term handles inside t-string step text — e.g. `t'a {g["Room"]} is booked'` where `g` is the project's glossary (see [glossaries.md](glossaries.md)). Term refs are what power the Glossary tab's per-term filter, and they render as pills. The `@scenario` name can carry pills the same way when its interpolations are all handles — `@scenario(t'a {g["Guest"]} checks in')` (glossary handles only; a parametrize value there needs `Template`). Name pills serve the reader, not story coverage — coverage counts step narration only, so a term the coverage needs must also appear in a step (see [stories.md](stories.md)). (Skip this rule if the project has no glossary yet.)
- **The code speaks the language too.** The glossary is a core part of the project's ubiquitous language, and a term ref puts that language directly next to code — check that each referenced term is reflected in the naming within the step: the body and the SUT names it directly calls. `File glossary` over a `FileGlossary` call matches by design (term names are natural language; the definition spells the class), but `{g["Reservation"]}` over code that only knows `Booking` is language drift — rename one side rather than let the vocabularies fork.
- **Tag orthogonally to the glossary — never duplicate a term.** A tag that restates a glossary term is redundant: filter those feature areas via the term instead, and make sure the scenarios reference that term. Tags carry only what the glossary can't: behaviour (`happy-path`, `validation`), mechanism (`parametrization`), and feature areas with no matching term. The `tag-shadows-term` lint rule enforces this mechanically.
- **Keep step text short.** A t-string with two or three pills reaches your line-length limit fast; move detail into the node structure rather than one long sentence.

## Keeping it truthful

- **A universal quantifier is a claim about every item.** A `then` saying "each", "every", "both", or "all" must assert every item it ranges over — "each slot becomes a term ref" backed by assertions on two of three slots overstates. Assert them all, or narrow the text to what is checked.
- **Stale narration is a stale assertion.** When a change touches a step *body*, re-read that step's *text* (and the scenario name) in the same edit and update it if the behaviour shifted. A behaviour change is a narration change.
- **When narration and body disagree, decide which side is wrong — the narration is not automatically the mistake.** A step or scenario name stating the intended behaviour over a body that checks something weaker, or that passes for a different reason than the name claims, has found a *broken test*: fix the body, keep the words. Editing the narration down to match such a body launders a bad test into a truthful-looking spec. Ask what the name promises, then whether the body would fail if that promise were violated.
- **Verify the narration reads truthfully before committing** (`pytest <selection> --given-md`). Narration is auditable, not verified: nothing mechanically checks semantic truth, so a step whose text overstates its body is a bug of the same severity as a wrong assertion.

## Mechanical counterparts

The narration lint (`pytest --given-lint=true`, or `given_lint = true` in `[tool.pytest]`) enforces the structural subset of these rules: `missing-phase`, `empty-step`, `then-without-check`, `check-outside-then`, `action-in-then`, `divergent-case-structure`, `tag-shadows-term`, and the opt-in `dead-term`. Only *error*-severity findings fail the run.

**Treat a `missing-phase` warning as a prompt to restructure, not to suppress.** It defaults to **warn**, so it never fails the run on its own, and it nearly always marks a hidden `when` rather than a genuinely two-phase scenario: apply the constructor rule above, or surface a parametrized input as `Annotated[..., given(Template('…'))]` so the inline block is free to narrate the action. `given_lint_ignore` (`missing-phase: <node-id glob>`) is a last resort, and it costs more than it looks: an entry that suppresses nothing raises `stale-ignore`, **always error-level, not downgradable via `given_lint_rules`, not itself ignorable**. Any selection that doesn't reach the suppressed node then fails on the stale entry alone — `pytest tests/one_file.py --given-lint=true` fails even when every collected scenario is clean.
