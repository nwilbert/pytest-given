# Glossary, tag and story hygiene

- A **dead term** (the opt-in `dead-term` lint rule) is a finding when it describes behavior nobody implemented: then it misleads. First check whether an undecorated test covers the row's behavior, or a step uses the term as plain text. If so, decorate the test or add the term ref. Otherwise, deleting the term is as often the fix as adding a reference. Don't accept references invented just to satisfy the rule. A term that is real vocabulary but that no scenario narrates is **not** a finding: the glossary documents the domain, not the suite's coverage.
- **Dilution** is the opposite finding: a row nobody would miss. Examples are a generic verb added to fill a story slot (a bare word belongs there), a concept listed twice under two names, or a term added only to render as a term ref. A small, precise glossary is better than one that just looks impressive.
- **Tool detail** in a definition is a finding: which component handles the term, where a screen or report shows it, how the code stores it. That belongs in the docs. A definition keeps only the behavior that defines the term.
- A **missing term** is a word that recurs across titles and steps for one domain concept but has no glossary row. Check first whether the glossary has the concept under another name; then the finding is drift (layer 2). Otherwise propose the term with a draft definition, and leave adding it to the user.
- An **oversized glossary** is a structural finding. A glossary only works when it is read as a whole, so one too long to read comfortably in one sitting probably covers more than one bounded context. Raise it as a design question: a suite supports only one glossary, so splitting by context means splitting the suite. Don't reduce the size by removing good terms.
- A `tag-shadows-term` lint finding is fixed by removing the tag. Tags carry only what the glossary can't (behavior, mechanism), so few tags is usually right; don't report it. A tag missing from some of the scenarios it describes is a finding, because filtering by it misses them. A work-item tag (`ticket/…`, `spec/…`) is the exception: it marks only what one piece of work added.
- An **uncovered story sentence** is a gap in the story's telling, not in the tests (untested behavior is layer 3). Note it, unless its declaration marks it as deliberate: a story maps the whole flow, including human work. [story-coverage.md](story-coverage.md) has the queries and how to explain *why* a sentence is uncovered.
