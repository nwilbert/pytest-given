Markdown report¶

The Markdown report is a run's scenarios as plain Markdown: one section per scenario, with its steps, attachments, parameter table and error. It reads well in a terminal, shows up as a readable diff in a pull request, and costs an AI agent a fraction of the tokens of the test code it narrates. The full example at the end of this page shows one.

Writing it¶

pytest --given-md              # print it to stdout
pytest --given-md=report.md    # write it to a file

Printed to stdout, the report sits between <!-- pytest-given:md:start --> and <!-- pytest-given:md:end --> markers, which separate it from pytest's own output. The report covers whatever the run selected, so pytest's -k, --lf and node IDs narrow it as usual.

To render it from a saved JSON report instead, without running the tests, use the standalone CLI: pytest-given report report-data.json --format md.

Reading it¶

  • The heading is the scenario title, led by its status: ✓ passed, ✗ failed, ○ skipped, ⊗ expected failure. A parametrized scenario adds its number of cases.
  • The line below it points at the test as file.py:line::test_name, then lists the scenario's tags and any skip or xfail reason. The examples are rendered with given_md_lines = false, so their anchors carry no line (see Diffs).
  • Steps are a list, each led by its phase in bold. Steps recorded inside another step, like those of a helper function, are nested under it. A term ref shows in guillemets, like «room».
  • Attachments follow their step after a 📎. A short one sits on the same line, and a longer one goes in a code block below it.
  • A parametrized scenario narrates its cases once, with {placeholders} where they differ, and then a parameter table. The table leads with a case ID column only when some case has a custom ID. It ends with a status column only when the cases differ in status. A failed case's error and any attachment too long for its cell follow the table, keyed by the row.
  • An error is a quote: the first line of the message, then the innermost frame of your code.

The Markdown report holds only scenarios. The glossary and the domain stories appear in the HTML report and the JSON, along with source links and full tracebacks.

Diffs¶

Commit the Markdown report, and a pull request shows what changed in the narration next to the code that changed it. This project commits its own self-report for that reason.

By default, every anchor carries a line, so inserting one test changes the anchor of every scenario below it in the file. Set given_md_lines = false (or pass --no-given-md-lines) to leave the lines out. When diffing two reports rendered by the CLI, pass --no-lines to both.

Reviewing narration¶

Add --given-md-source to end each scenario with its test function, each line under its number in the file. Step text and step body then sit side by side, which makes it quick to check that the narration says what the code does. Only the test function is shown, not the step fixtures or helpers it uses.

All Markdown flags are listed under pytest options.

Example¶

The Coffeeshop example's report, as committed in examples/coffeeshop/coffeeshop.md, where GitHub also shows it rendered. The Examples page links every example's Markdown report.

# pytest-given — Coffee Shop Example

## ✓ Buying a coffee takes one from the machine
`examples/coffeeshop/test_coffeeshop.py::test_buy_coffee` · checkout

- **given** a coffee machine with 10 coffees
- **when** I buy a coffee
- **then** the machine has 9 coffees left
    - 📎 Machine state:
        ```
        {
          "coffees": 9,
          "price": 2,
          "water_ml": 1000
        }
        ```

## ✓ Plain text attachment
`examples/coffeeshop/test_coffeeshop.py::test_text_attachment`

- **given** a coffee machine with 10 coffees
- **given** a printed receipt
    - 📎 Receipt:
        ```
        Coffee x1     $2.00
        ----------------
        Total:        $2.00
        ```
- **when** the total line is read back
- **then** it shows the \$2.00 total

## ✓ Generator fixture with `yield` and *teardown*
`examples/coffeeshop/test_coffeeshop.py::test_generator_fixture`

- **given** a database connection
- **when** I run a query
- **then** the connection is **open** and the query was logged

    - **when** the balance is updated
- **then** the coin is accepted
- **then** a coffee is dispensed

        - 📎 Final state:
            ```
            {
              "coffees": 9,
              "price": 2,
              "water_ml": 1000
            }
            ```

## ✓ Top-level `given` block and deeply nested steps
`examples/coffeeshop/test_coffeeshop.py::test_complex_order` · checkout, loyalty, discounts, ticket/CS-7

- **given** a coffee machine with 10 coffees
- **given** a loyalty card with 5 points
- **when** I place a large order
    - **when** I select 3 coffees
    - **when** I apply loyalty discount
        - **when** the loyalty card is validated
        - **when** the discount is calculated
- **then** the order is processed correctly
    - **then** the coffee count is updated
    - **then** the loyalty points are deducted
        - **then** the remaining points are valid
            - 📎 Loyalty state:
                ```
                {
                  "points": 2
                }
                ```
- **then** the machine state is consistent
    - 📎 Final machine state:
        ```
        {
          "coffees": 7,
          "price": 2,
          "water_ml": 1000
        }
        ```
